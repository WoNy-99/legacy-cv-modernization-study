# 과거 실험 기록

시기는 대화가 남은 시점입니다. 날짜별 기록은 서로 다른 작업일 수 있으며 하나의 연속된 성공 이력으로 합치지 않았습니다. 근거 표시는 [문제 정의](problem-definition.md)를 따릅니다.

## E01 · Geometric augmentation 전환

**2026-08 · LOG + OBS · 추가 학습 진행, 품질 문제 미해결 보고**

**목적:** 기하 증강 설정과 학습 진행이 결과에 미치는 영향을 이해하기.

**설정 근거:** 사용자는 약 58,000개 입력, 약 70,000 iteration까지 warp ON, 약 120,000까지 OFF로 진행했다고 설명했습니다. 이후 다시 ON으로 변경했다고 보고했습니다. 이 특정 실행의 해상도·배치·optimizer 전체 설정은 텍스트만으로 묶어서 확정하지 않았습니다. 다른 실행의 256 / batch 8 설정을 여기로 가져오지 않았습니다.

다음은 재활성화 이후 붙여넣은 출력에서 숫자 열만 전사한 것입니다. `loss_1`, `loss_2`는 원래 두 출력 열을 익명화한 이름이며 새로운 지표나 검증 손실이 아닙니다.

| iteration | 표시 반복 시간 (ms) | loss_1 | loss_2 |
|---:|---:|---:|---:|
| 124262 | 293 | 0.7716 | 0.5938 |
| 128973 | 294 | 0.7009 | 0.5264 |
| 133985 | 305 | 0.6804 | 0.5069 |
| 139033 | 296 | 0.6655 | 0.4962 |
| 144079 | 311 | 0.6546 | 0.4855 |

**관찰:** 이 구간에서 두 loss가 감소했습니다. 후속 대화에서는 추가 학습과 다시 내보내기 이후에도 품질이 어색하다는 보고가 이어졌습니다.

**한계:** 시간 경과에 따른 추가 학습과 증강의 효과를 분리하지 않았습니다. OFF 유지 대조군이나 고정 평가 집합은 없습니다. 품질 문제가 남았다는 것은 사용자의 관찰이며 이미지를 현재 재평가한 결과가 아닙니다.

**교훈:** loss 감소만으로 원하는 품질이 확보되었다고 판단할 수 없었습니다.

## E02 · 사전 학습 상태 재사용과 설정 확인

**2026-08 · LOG + OBS · 적용을 시도했으나 로딩 근거 불충분**

- 이전에는 저장된 학습 상태를 이어 사용하는 데 실패했다고 설명했습니다.
- 이후 사전 학습 상태를 적용해 진행 중이라고 보고하면서, 실제 적용 여부를 확인하는 방법을 질문했습니다.
- 해당 실행의 출력에는 resolution 256, batch 16, AdaBelief 활성, geometric warp 활성, `lr_dropout` 비활성이 나타납니다.
- 사용자는 이전보다 입력 규모가 커졌다고 설명했습니다. E01과 동일한 실험으로 취급하지 않습니다.

후속 대화에서 약 150,000 iteration에 warp를 껐다고 보고했으며, 다음 숫자가 남아 있습니다.

| iteration | 표시 반복 시간 (ms) | loss_1 | loss_2 |
|---:|---:|---:|---:|
| 160119 | 386 | 0.4651 | 0.3656 |
| 163698 | 385 | 0.4235 | 0.3189 |
| 167524 | 385 | 0.4084 | 0.3052 |
| 171360 | 386 | 0.3985 | 0.2972 |
| 175172 | 379 | 0.3921 | 0.2904 |
| 179019 | 386 | 0.3854 | 0.2849 |
| 182867 | 379 | 0.3825 | 0.2813 |

학습 출력은 확인되지만, 사전 학습 상태의 정확한 로딩·동등성·재사용 효과는 현재 검증할 수 없습니다. E01과 loss 크기를 직접 비교해 더 좋은 실행이라고 결론 내리지 않습니다.

## E03 · 해상도와 학습률 관련 옵션

**2026-08 · OBS + 일부 LOG · 사용 설명 및 적용 여부 질문**

사용자는 해상도 256·284·320 중 선택해 사용하며, 초기 warp ON → 이후 OFF → `lr_dropout` 활성 순서로 진행하는 습관을 설명했습니다. 다른 대화에서는 이번 실행에서 `lr_dropout`을 바꾸지 않았다고 설명했습니다.

따라서 “옵션을 사용한 경험”과 “이 실행에서 적용했는가”를 구분합니다. 해상도별 성능표나 학습률 옵션의 효과를 입증한 비교 결과는 없습니다.

## E04 · 배치·메모리 관찰

**2026-08 · LOG + OBS · 비통제 관찰**

batch 8→16 변경과 반복 시간 증가를 보고했습니다. 별도의 후처리 작업에서는 여러 보정 기능을 켠 상태에서 OOM을 보고했습니다. 두 사건은 다른 작업 단계이며, 학습 batch 16이 OOM의 원인이라고 연결하지 않습니다. 수치와 제약은 [성능 관찰](performance-notes.md)에 정리했습니다.

## E05 · 후처리 버전 차이와 품질

**2026-06~08 · OBS · 회귀 의심, 인과 미확정**

공개 문서에서는 서로 다른 후처리 버전을 Pipeline A / B / C로 표현합니다. 이는 실험 조건을 숨기고 동일하다고 주장하기 위한 이름이 아닙니다.

- A↔B 관련 보고: 흐림 감소 후 경계선이 두드러지는 trade-off를 설명했습니다.
- B↔C 관련 보고: 이전보다 경계·윤곽·색 일관성이 부자연스럽다고 설명했습니다.
- 설정을 바꾼 뒤 조금 나아진 것 같다는 보고와, 여전히 문제가 남았다는 보고가 있습니다.
- 더 최신 버전으로 해결 가능한지 질문한 기록은 있지만, 그 버전의 시험 성공으로 간주하지 않습니다.

입력과 학습 상태, preset이 모두 동일한 비교는 아닙니다. “최신 버전이 품질을 악화시켰다”는 확정 결론 대신 **동일 조건의 버전 비교가 필요했던 사례**로 기록합니다.

## E06 · 실행 환경과 UI 기동

**2026-09 · LOG + OBS · 부분 기동, 전체 검증 없음**

- PyTorch import 과정의 `ModuleNotFoundError` 출력이 있습니다.
- ONNX Runtime에서 GPU 실행 공급자 초기화 오류 및 재시도 출력이 있습니다.
- 이후 ONNX Runtime 1.18.0에서 CUDA 실행 공급자가 목록에 표시된 출력이 있습니다. 목록 표시는 전체 모델의 GPU 실행 성공과 다릅니다.
- 별도 출력에서는 Gradio API 정보 생성과 JSON schema 변환 경로에서 예외가 발생했습니다.
- 의존성 버전 변경 후 기동 메시지가 출력된 기록이 있으나, 후속 작업에서는 CPU 사용 증가와 처리 중단을 보고했습니다.

정확한 오류 원인과 해결의 완결성은 [실패 분석](failure-analysis.md)에 구분했습니다. 당시 버전을 현재의 권장 설치 조합으로 제시하지 않습니다.

## E07 · 입력 검증·평가 준비·작업 복구

**2026-04~05 · LOG + REPORT + OBS · 부분 진행 및 중단**

입력 조건 불일치로 추출 전 중단했다는 보고, 조건을 맞춘 뒤 추출·메타데이터 틀 생성까지 진행했다는 보고가 있습니다. 자동 라벨링 후 필요한 연속 구간이 없다는 결과도 전달되었습니다. 미검토 항목과 승인 상태는 구분해야 했습니다.

백업에서는 디렉터리 생성 실패와 파일 I/O 오류가, 반복 삭제에서는 `pathspec` 오류가 남았습니다. 후속 검증 보고는 일부 정리가 이미 커밋되었다고 설명했습니다. 현재 보관본의 무결성이나 전체 복구를 인증할 수는 없습니다.
