# Lessons learned

## 1. Loss와 품질은 다른 확인 항목

증강을 다시 켠 이후 두 loss 출력이 감소했지만, 후속 품질 문제 보고가 이어졌습니다. loss의 감소를 원하는 품질이나 일반화 확보로 간주하지 않게 되었습니다. 통제된 평가 없이는 특정 설정의 효과도 단정할 수 없습니다.

## 2. 버전 비교는 조건 고정부터

이전 버전이 더 좋아 보인다는 관찰은 유효한 조사 출발점입니다. 하지만 입력·학습 상태·preset까지 다르면 버전만을 원인으로 지목할 수 없습니다. “최신이 항상 좋다”거나 “구버전이 항상 좋다”는 결론 대신 비교 조건을 먼저 기록해야 합니다.

## 3. 기동 성공과 전체 성공은 다름

패키지 설치, GPU 공급자 목록 확인, 웹 UI 기동, 실제 작업 완료, 장시간 안정성은 별도 단계입니다. 일부 단계의 성공을 전체 해결로 확대하지 않습니다.

## 4. 반복 시간과 메모리에는 측정 범위가 필요

batch를 바꾼 뒤 한 iteration이 느려졌다는 사실만으로 효율 저하나 개선을 확정할 수 없습니다. 실제 작업량과 시간 범위를 확인해야 합니다. OOM 역시 발생 단계와 함께 기록해야 원인을 잘못 연결하지 않습니다.

## 5. AI 제안·실행 보고·직접 확인을 구분

AI 도구를 분석과 리뷰에 활용했지만 모든 설명을 사실로 취급하지 않았습니다. 계획은 PLAN, 사용 경험은 OBS, 출력은 LOG, 전달된 작업 보고는 REPORT로 구분했습니다. 현재의 문서화 역시 이 구분을 따릅니다.

## 6. 실패한 코드도 보존할 가치가 있음

과거 코드를 삭제해 현재 재현과 기여 입증에 제약이 생겼습니다. 다음 시도에서는 작은 커밋, 환경 기록, 변경 이유, 시험 결과를 함께 남겨야 합니다. 백업 명령 실행만으로 보관이 완료되었다고 판단하지 않습니다.

## 최종 상태

남아 있는 실행 기록으로 설명할 수 있는 기술적 경험은 있으나 전체 현대화는 미완료입니다. 지금 제공하는 것은 회고, 설계안, 새 보조 템플릿입니다. 면접이나 문서에서도 실험 경험과 구현 완료 실적을 구분합니다.
