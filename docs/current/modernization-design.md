# 현재: 현대화 설계

**상태: 설계안. 아래 구조는 구현된 시스템이 아닙니다.**

과거 설계 논의를 현재의 문서 형태로 정리했습니다. 삭제된 코드를 복원하거나 실행 검증을 마친 재구현으로 표현하지 않습니다. 기존과 비교할 기준 실행 환경이 확보되지 않으면, 새로운 구현을 만들더라도 기존 동작과의 동등성을 주장할 수 없습니다.

## 설계 목표

1. 환경 변경과 동작 변경을 구분합니다.
2. 입력 검사와 평가 승인을 구분합니다.
3. 정확성 확인 이후에 성능 실험을 수행합니다.
4. 변경 범위와 검증 결과가 함께 남도록 합니다.

## 제안하는 검증 순서

```mermaid
flowchart LR
    A[입력 조건 검사] --> B[전처리 계약 확인]
    B --> C[연산 단위 비교]
    C --> D[파이프라인 비교]
    D --> E[안정성 확인]
    E --> F[성능 실험]
```

앞 단계의 근거가 없으면 뒤 단계의 성공을 선언하지 않는다는 설계입니다. 이 도식은 과거 실행 결과가 아닌 현재 작성한 설명입니다.

## 변경 전에 명시할 계약

| 영역 | 보존하거나 명시적으로 검토할 항목 | 제안하는 확인 방법 |
|---|---|---|
| 입력 | 크기, 채널, 값 범위, 시간 단위 | 조건을 어긴 입력의 명시적 거부 |
| 전처리 | 보간, 경계 처리, 정규화, 처리 순서 | 작은 테스트 입력의 중간 결과 비교 |
| 무작위 처리 | 난수 사용 위치와 증강 규칙 | 고정 조건 비교와 분포 확인을 구분 |
| 연산 | 텐서 배치, 차원, 패딩, 활성화 | 연산별 shape·수치 비교 |
| 학습 설정 | 손실 정의, 갱신 규칙, 설정 의미 | 설정 해석과 제한된 단계 결과 확인 |
| 실행 | 장치, 정밀도 정책, 의존성 버전 | 환경 기록과 반복 실행 |

## 정확성 모드와 성능 모드

**정확성 모드 제안:** 명시적인 FP32 기준부터 시작하고, 자동 혼합 정밀도나 그래프 최적화 등은 비교 기준을 세운 뒤 별도 변경으로 다룹니다. 허용 오차는 현재 정해 두지 않습니다. 기준 출력과 요구 수준을 확보한 후 연산별로 정해야 합니다.

**성능 모드 제안:** 입력 공급, 전처리, 장치 전송, 연산 시간을 나눠 측정한 다음 병목 후보 하나씩 변경합니다. worker 수, prefetch, 전송 방식 등의 조정은 후보일 뿐, 이 저장소에서 적용하거나 효과를 확인한 기능이 아닙니다.

## 작은 작업 단위

각 변경에 다음을 기록하는 방식을 제안합니다.

- 목적: 무엇을 바꾸는가.
- 허용 범위: 어떤 파일 또는 구성 요소만 바꾸는가.
- 비변경 범위: 어떤 동작은 유지해야 하는가.
- 수용 조건: 어떤 결과가 있어야 완료인가.
- 실제 결과: 수행, 미수행, 실패, 부분 통과를 구분.
- 되돌리기: 이전 상태와 비교 자료를 어떻게 보존하는가.

현재는 이 형식의 설계 문서만 있습니다. 실행 가능한 CLI, 전환 도구, 학습·추론 모듈은 제공하지 않습니다.
