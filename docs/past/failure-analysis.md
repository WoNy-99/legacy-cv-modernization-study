# 과거: 실패 분석과 회고

전체 현대화는 완료하지 못했습니다. 다음은 남은 기록으로 설명할 수 있는 문제이며, 모든 중단 원인을 밝혀낸 사후 분석은 아닙니다.

| 문제 | 기록으로 확인 가능한 범위 | 확정하지 않은 내용 | 현재 설계에 반영할 점 |
|---|---|---|---|
| 입력 조건 불일치 | 처리 전 조건 위반으로 중단했다는 보고 | 조건 자체가 모든 작업에 최적이라는 주장 | 처리 전 조건 검사, 조건 변경 시 별도 기록 |
| 평가 준비 지연 | 자동 라벨링 후 유효 구간이 없었다는 결과 | 추정기 또는 입력만의 단독 책임 | 형식 통과·라벨 검토·평가 승인을 분리 |
| 기본값과 판정의 혼동 위험 | 초기 보고와 후속 보고의 메타데이터 기본값이 다름 | 초기 기본값이 실제 잘못된 승인을 유발했다는 주장 | 미검토 값은 명시적으로 미검토 상태 유지 |
| 백업 및 Git 정리 오류 | 디렉터리 생성 실패, 반복 삭제 오류 출력 | 당시 모든 자료가 안전하게 복구되었다는 주장 | 백업 검증을 정리 작업의 선행 조건으로 설정 |
| 관찰과 원인 설명의 혼동 | CPU 변경 후 속도 변화와 시스템 문제 보고 | 병목 해소, 메모리 문제의 단정 | 조건 기록·계측·반복 시험 없이는 가설 유지 |
| 과거 구현의 보존 실패 | 현재 원본 코드가 없다는 본인 확인 | 구현 완성도나 코드별 기여율 | 앞으로는 작은 변경과 검증 결과를 함께 보존 |

## 접근 방식에서 아쉬웠던 점

### 1. 평가 준비 비용을 충분히 낮추지 못함

입력 확보·조건 검사·라벨 검토에서 여러 차례 막혔습니다. 그렇다고 통과를 위해 기준을 임의로 낮추면 비교 의미가 달라집니다. 다음에는 작은 검증 가능한 범위부터 시작하고, 입력 준비가 막히면 해당 단계에서 멈춘 이유를 남기는 편이 낫습니다.

### 2. AI 보고와 실제 상태를 분리할 필요

계획 문구, 완료 보고, 실제 Git 상태가 항상 같은 시점을 가리키지는 않았습니다. 또한 AI 설명 중에는 사용자가 재확인을 요구한 부분도 있었습니다. 보고서의 표현만 믿고 다음 단계로 넘어가지 않고, 범위를 좁힌 실제 확인 결과를 남기는 절차가 필요했습니다.

### 3. 측정 이전에 기대 효과를 넓게 논의함

학습 시간, GPU 활용, 메모리 효율 등의 개선 방향을 논의했지만 이를 검증하는 기준 환경과 비교 결과는 남아 있지 않습니다. 기대 효과는 설계의 동기일 뿐 성과가 아닙니다.

## 얻은 판단 기준

- 일부 단계의 PASS와 전체 완료를 구분합니다.
- 실행하지 않은 시험은 실패나 성공 대신 **미수행**으로 기록합니다.
- 원인 추정은 반증 가능한 시험으로 이어질 때만 다음 작업의 근거로 사용합니다.
- 삭제·정리보다 보존과 상태 확인을 먼저 합니다.
- 성공하지 못한 시도를 기록할 때도 사실, 해석, 다음 제안을 나눕니다.
